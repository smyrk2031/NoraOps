# テストと動作確認

NoraOps の品質確認は **3 層** に分ける。目的が違うので混同しない。

| 層 | 誰向け | いつ | 何を見るか |
|----|--------|------|------------|
| **① スモーク（GUI）** | 運用・公開しながら開発 | 環境構築後・設定変更後・不調時 | 接続・権限・設定の「生きているか」 |
| **② ユニットテスト** | 開発・CI | コード変更・PR 前 | ロジックの回帰（オフライン可） |
| **③ 手動 E2E** | デモ・リリース前 | 大きな機能追加後 | 保存 → Gitea → Runner 起動の縦通し |

**日常の「主要機能は動く？」→ ① で足りる。**  
**zip 解凍や session 参照ルールなど → ②。**  
**実際に tk が起動するか → ③**（[縦通し体験手順.md](./縦通し体験手順.md)）。

## ① スモーク（GUI 動作確認）

### 実行方法

| 場所 | 操作 |
|------|------|
| **ポータル TOP** | `http://127.0.0.1:8000/` → 「NoraOps 動作確認」 |
| **ブラウザ直** | `http://127.0.0.1:8000/noraops/diagnostics/run` |
| **VS Code** | コマンド `NoraOps: 動作確認（主要機能）`、またはホーム / Runner の「動作確認」 |

前提: FastAPI 起動済み、拡張の `noraops.server.baseUrl` が合っていること。

### サーバー側のチェック項目

実装: `nora-backend/app/noraops/services/diagnostics.py`  
API: `GET /api/v1/noraops/diagnostics/run` · HTML: `/noraops/diagnostics/run`

| ID | 項目 | 意味 |
|----|------|------|
| `config_gitea_url` | GITEA_BASE_URL | `.env` の Gitea URL |
| `config_gitea_token` | GITEA_TOKEN | サーバー用 PAT の有無 |
| `server_git` | サーバー git | **PATH 上の git**（保存 push 用。拡張の portable git とは別） |
| `artifacts_dir` | artifact キャッシュ | 書き込み可能か |
| `gitea_token_format` | トークン形式 | `gitea_pat_` 等の妥当性 |
| `gitea_user` | Gitea ユーザー API | トークンで API 到達 |
| `gitea_create_repo` | リポ作成権限 | 新規保存に必要 |
| `push_session_write` | 保存用セッション | 短命トークン発行 |
| `push_session_read` | Runner 用セッション | artifact DL 用 |
| `tools_manifest` | uv manifest ファイル | `data/tools/windows-x64/manifest.json` の存在 |

### 拡張側のチェック項目（＋サーバー取り込み）

実装: `vscode-extension/src/noraops/healthCheck.js` · UI: `healthCheckUi.js`

| ID | 項目 | 意味 |
|----|------|------|
| `cfg_server` | baseUrl 設定 | VS Code `noraops.server.baseUrl` |
| `portal_health` | FastAPI | ポータル API 死活 |
| `checks_rules` | チェックルール | ルール JSON 配布 |
| `gitea_status` | Gitea（プロキシ） | サーバー経由の接続・作成権限 |
| `tools_uv` | uv（クライアント） | ローカル uv の導入（**git は不要**） |
| `session_write` | 保存セッション | API で発行できるか |
| `catalog` | Runner カタログ | 公開アプリ一覧 API |
| `srv_*` | `[サーバー] …` | 上記サーバー診断を **そのまま取り込み** |
| `local_storage` | ローカルキャッシュ | `venvs` / `runner-apps` の容量参考 |

### 拡張 vs サーバー（重複の見方）

```text
拡張の動作確認 ＝ クライアント固有の項目 ＋ サーバー診断 API の結果（[サーバー] プレフィックス）

サーバー単体の動作確認 ＝ サーバー上だけ分かる項目（PATH の git、artifact ディレクトリ等）
```

| 観点 | 拡張のみ | サーバーのみ | 両方（見方が違う） |
|------|----------|--------------|-------------------|
| 例 | baseUrl、uv、ローカル容量 | サーバー git、artifact dir、manifest ファイル | Gitea、セッション |

**ブラウザだけ**でもサーバー運用は確認できる。**拡張から**だと設定ミスとクライアント uv まで一度に見られる。

### スモークで見ないもの

- 実際の zip 保存・Gitea push の成功
- artifact のビルド完了・GUI アプリの起動
- ポリシーチェックの網羅

→ ② または ③ でカバー。

## ② ユニットテスト

### 拡張（Node.js `node --test`）

```powershell
cd vscode-extension
npm test
```

| ファイル | 対象モジュール | 内容 |
|----------|----------------|------|
| `test/appEntry.test.js` | `appEntry.js` | manifest からの entry 解決 |
| `test/checkRunner.test.js` | `checkRunner.js` | glob マッチ・tests 除外 |
| `test/pathsMeta.test.js` | `pathsMeta.js` | 日本語フォルダ名 → slug |
| `test/repoMeta.test.js` | `repoMeta.js` | **session のみ**で Gitea 名を読む（origin フォールバック禁止） |
| `test/toolManager.test.js` | `toolManager.js` | semver 比較・sha256 |

**現状: 10 tests（オフライン・FastAPI 不要）**

追加の目安:

- 保存・zip・API を触ったら → `workspaceZip.js` / `repoMeta.js` 周辺
- ツール配布を触ったら → `toolManager.js`（uv のみ必須の前提をテストに書く）

### サーバー（pytest）

```powershell
cd nora-backend
# venv 推奨
.\.venv\Scripts\Activate.ps1
pytest tests/ -v
```

| ファイル | 対象 | 内容 |
|----------|------|------|
| `tests/test_zip_utils.py` | `zip_utils.py` | zip パストラバーサル拒否、`.env` 検出 |

**Gitea・DB は不要**（純粋な関数テスト）。

追加の目安:

- `repo_save` / `artifact_builder` を触ったら → モックまたは tmp_path で pytest 追加
- `diagnostics.py` の分岐を増やしたら → `tests/test_diagnostics.py`（設定モック）

## いつ何を走らせるか（運用メモ）

| タイミング | 推奨 |
|------------|------|
| FastAPI / `.env` 変更後 | ① サーバー画面 |
| 拡張の設定・保存周りを変更後 | ① 拡張 + `npm test` |
| `zip_utils` / 保存 API を変更後 | `pytest` + ③ の保存ステップ |
| 公開ビルド前 | ① + ② 全部 + ③ 主要シナリオ |
| 本番障害の切り分け | ① でサーバー/クライアントどちらが赤か確認 → 該当層のログ |

## メンテナンス方針（この MD の更新ルール）

1. **スモーク項目を増減したら** → 上の「チェック項目」表と [機能一覧とAPI.md](./機能一覧とAPI.md) を同期する。
2. **テストファイルを追加したら** → 「ユニットテスト」の表に 1 行追加し、件数（`10 tests` 等）を更新する。
3. **git 不要化など方針が変わったら** → 「スモークで見ないもの」「拡張 vs サーバー」を見直す。
4. **CI を入れるとき** → ② のコマンドをそのままパイプラインに載せ、① はステージング手動または定期実行。
