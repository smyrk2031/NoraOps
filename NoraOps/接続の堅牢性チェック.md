# NoraOps 接続の堅健性チェック（多角的レビュー）

「盤石か？」への回答: **ローカル開発と単一サブパス IIS 前提では実用レベル**。以下の穴は運用・設定でカバーが必要です。

## 盤石な部分

| 領域 | 内容 |
|------|------|
| URL 正規化 | サブパス `/NoraOps`、誤って `/api/v1` まで貼った補正 |
| 設定 UI | 専用タブ・接続テスト・保存・初回ガイド |
| 拡張 → API | Node `http`/`https`（**既定で HTTP_PROXY を使わない**） |
| サーバー → Gitea/Azure | httpx **`trust_env=False` 既定**（`NORAOPS_HTTP_TRUST_ENV=0`） |
| オフライン | チェックルールはバンドル同梱でサーバー不可でも一部動作 |

## 残るリスク（要運用対応）

### 1. 社内プロキシ（ご指摘）

| 層 | 挙動 | 対策 |
|----|------|------|
| **FastAPI (httpx)** | 旧: `HTTP_PROXY` で Gitea/Azure がプロキシへ | ✅ 既定 `trust_env=False`。外向きのみプロキシ必須なら `NORAOPS_HTTP_TRUST_ENV=1` |
| **VS Code 拡張** | Node API は直接接続 | 設定タブでプロキシ env を表示・ヒント |
| **ブラウザ** | ポータルはプロキシ経由のことがある | 接続テストは **拡張から API** を叩く（ブラウザと別経路） |

### 2. IIS + ARR リライト

| 失敗例 | 症状 | 確認 |
|--------|------|------|
| パス剥がし忘れ | 404 / HTML エラーページ | ブラウザで `{URL}/api/v1/portal/health` が JSON |
| HTTPS 終端ずれ | Mixed content | 拡張も https の同じホストを指定 |
| WebSocket 不要 | — | 現状 REST のみ |

### 3. TLS（社内 CA）

| 症状 | 対策 |
|------|------|
| `UNABLE_TO_VERIFY_LEGO` | OS / VS Code に社内 CA を信頼させる、検証用は http |
| 自己署名 | 本番は正式証明書推奨 |

### 4. まだ弱い機能（既知）

| 項目 | 状態 |
|------|------|
| Copilot 個人課金の自動検出 | 同意 + ヒントのみ |
| サムネ Webview 貼り付け | クリップボードから保存で回避 |
| 双方向プロキシ必須の拠点 | `NORAOPS_HTTP_TRUST_ENV=1` を検証してから |

### 5. セキュリティ境界

| 項目 | 注意 |
|------|------|
| サムネ API | 公開アプリのみ・認証なし（意図） |
| push token | 短期セッション |
| `.env` in zip | 保存時除外（要セキュリティチェック継続） |

## 接続テストで見る項目

**NoraOps 設定** → 接続テスト:

1. URL 解釈
2. クライアントのプロキシ env（情報）
3. NoraOps API（ポータル）— **必須**
4. チェックルール
5. ランタイム設定（Gitea）
6. Runner カタログ

「ブラウザでトップが開く」だけでは不十分。**health API が JSON** であることを確認してください。

## 推奨 `.env`（サーバー）

```env
NORAOPS_HTTP_TRUST_ENV=0
GITEA_BASE_URL=http://127.0.0.1:3000
```

社内 Gitea は **ループバック or プライベート IP 直結** が無難です。

## 推奨 NO_PROXY（開発者 PC）

社内 NoraOps / Gitea サーバーへ:

```text
NO_PROXY=localhost,127.0.0.1,10.0.0.0/8,192.168.0.0/16,.contoso.local
```

（組織のポリシーに合わせて調整）
