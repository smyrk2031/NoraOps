# NoraOps 前提と全体像（4 本柱）

思想の詳細は [構想資料.md](./構想資料.md)。**製品をどう分解するか**の前提だけここに固定する。

## 4 つの主役（この順で頭に置く）

```
  [Gitea]          アプリの保管・バージョン（正本。社内には大量のリポが存在してよい）
      ↑ 参照
  [FastAPI]        解析（SEC / LICENSE / 類似…）＋ 【承認】→ ユーザー向け「公開カタログ」だけを束ねる
      ↑ API（検索ヒットは承認済みリポ×バージョンのみ）
  [VS Code 拡張]   Creator：作成・保存・Gitea ／ Runner：承認済み検索・uv 実行（旧ポータル相当）
      ↑ 同じ .vsix
  [Tauri クライアント]  （将来）軽量 Runner のみ — 同じ FastAPI API
```

| 柱 | 一言 | やることの例 |
|----|------|----------------|
| **① Gitea** | 置き場 | Push / Release／**リストに出す義務はない**（社内のみのリポも可）。 |
| **② FastAPI** | 頭脳・ゲート・配布ページ | 横断解析、**承認**で公開カタログ化。**公開済みだけ**が Runner 検索に載る。**トップで .vsix 案内**。 |
| **③ VS Code 拡張** | 唯一の必須クライアント（Phase1） | **Creator** + **Runner**（ポータル機能は拡張内）。詳細 [ポータルとクライアント.md](./ポータルとクライアント.md)。 |
| **④ Tauri（将来）** | 軽量 Runner | VS Code を避けたい部門向け。API は ② と同じ。 |

「その先」の PR 支援・匿名チャット等はフェーズ分割（[フェーズ進行.md](./フェーズ進行.md)）。

## 公開の流れ（典型）

1. 開発者が Gitea にアプリを載せる（任意の公開範囲）。
2. FastAPI が解析（ポリシー・ライセンス等）し、運用管理者が **リポジトリとバージョン（タグ／Release）を承認**する。
3. **承認された組み合わせだけ**が **公開カタログ** に載り、クライアントツールの **検索にヒット**する。
4. 利用者が「アプリを使う」などで **最小限のファイル**を取得し、`uv` で環境を作り実行する。
5. IDE 利用者は拡張で同じ「公開」の世界観で補助機能を受ける。
