## 5. チェックルール — FastAPI を正本にする案（推奨）

**「同期」ではなく「同じ定義を配る」**。拡張・将来のサーバ静的解析が **同じ `ruleId`** を使う。

```text
拡張同梱 JSON（オフライン用フォールバック）
        ↓ 上書きマージ（etag が新しいときだけ）
GET /api/v1/checks/rules  ← 運営がここを更新
        ↓
CheckRunner（拡張）          Analyzer（FastAPI・Phase1b 以降）
```

### 5.1 エンドポイント（FastAPI-17）

`GET /api/v1/checks/rules`

| 項目 | 内容 |
|------|------|
| レスポンス | `{ "schema": "nora.rules-bundle/1", "version": "2026.05.18-1", "etag": "…", "security": { "rules": [...] }, "repo_policy": { "rules": [...] } }` |
| 形式 | [チェック仕様.md](./チェック仕様.md) の `.rules.json` と **同一スキーマ** |
| キャッシュ | 拡張は `etag` を保存。`If-None-Match` で **304** |
| 失敗時 | **同梱 JSON** のみで動作（オフラインと同じ） |

`POST /api/v1/checks/run`（Phase1b・任意）

| 項目 | 内容 |
|------|------|
| 用途 | サーバ側でリポを clone/tarball して **同じルール**で走らせる（横断解析） |
| Phase1a | **未実装でよい**。ルール API だけ先に切る |

### 5.2 なぜスマートか

- 運営が **JSON を差し替えるだけ**で全社の SEC ルールを更新できる（拡張再配布不要）。
- 拡張の結果とサーバ解析の **ruleId・message が一致**する。
- 「動機」ではなく **単一の契約**（エンドポイント定義）— おっしゃる通りそのイメージでよい。

### 5.3 拡張のマージ順（確定案）

1. 同梱 `resources/checks/*.rules.json`  
2. `GET /checks/rules`（成功時、etag 新しければ置換）  
3. （Phase1a では **なし**）リポジトリローカル override

## 6. オフライン・push 失敗

| 状態 | 保存 | push | セキュリティ実行ブロック |
|------|------|------|--------------------------|
| **オンライン** | 可 | 試行し成功なら「クラウド済」 | **あり**（オンラインルール＋同梱） |
| **オフライン** | 可 | **スキップ**（エラーにしない） | **なし**（閉じた環境＝流出リスク低いとみなす） |
| **オンラインだが push 失敗** | 可 | 「クラウド未送信」＋再送ボタン | **あり** |

**UI**

```text
✓ 保存済み（この PC のみ）   ← オフライン
✓ 保存済み・クラウド済
☁ クラウド未送信  [ 再送 ]
```

- オフラインでも **ローカル git 履歴**は増える（Excel の「保存」に近い）。
- オンライン復帰後、次の保存 or **[ 再送 ]** で push。
