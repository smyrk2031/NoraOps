## フェーズ設計の原則（ここを大事にする）

1. **Phase1 はコアだけ**  
   Gitea を正本にした **解析 → チェック → ダッシュ → 承認 → 公開カタログ → クライアント／拡張で実行** までが、**生成 AI なし・GitHub なし**でも **一貫して動く**閉じた製品になることをゴールにする。

2. **フェーズを進めても「その時点の製品」は整合している**  
   Phase2 を止めても Phase1 の範囲で運用できる。Phase3 を止めても Phase2 までで運用できる。**後続フェーズに依存して初めて成立する**並びは避ける（依存は **ID で明示**し、オプションは **フラグ／未設定＝無効**）。

3. **生成 AI・GitHub は「実装するが、使うかは導入社に任せる」**  
   - **コード・設定フック・API は先に入れる**（未実装のまま先送りにしない方針でもよいが、方針として **「載せられる状態」まで持っていく**）。  
   - **既定はすべて OFF**（環境変数・管理画面で **明示的に ON** した導入社だけが課金・外部接続が発生）。  
   - **コア（承認・公開カタログ・uv 実行）は AI / GitHub が無くても同じ UX**。

4. **機密（Sec）はフェーズをまたいで厳しめ**  
   ローカルでも **平文 PAT 置き**を避ける等、細部は妥協しにくい（[Sec](#sec横断機密ローカル含む)）。

この原則に沿って表を読むと、**実装の背骨として十分に使える**想定。注意点は文末の [レビューメモ](#レビューメモこの文書で足りるか) を参照。

### FastAPI-10 で想定していること（テレメトリ）

**目的**: 「どの機能がどれくらい使われたか」「失敗がどこで多いか」を **導入社の運用・改善**のために見る。**個人の行動プロファイルや広告配信には使わない**想定。

**受信の形（現行 `softrail-server` に近い）**

- **HTTP POST**（例: `/api/telemetry/events`）に **バッチ or 単発**の JSON。
- 1 件あたりおおよそ **`event_type`**（短い識別子）、**`source`**（`extension` / `client_portal` 等）、**`payload`**（小さな JSON）、サーバ側で付与する **接続元 IP・User-Agent**（監査用。PII ではないが組織方針でマスク可）。

**`event_type` / `payload` の例（PII を載せない）**

| event_type（例） | payload に入れてよい例 | 入れない例 |
|-------------------|------------------------|------------|
| `tool_bootstrap_ok` / `tool_bootstrap_fail` | uv のバージョン、失敗理由コード | メール、氏名 |
| `catalog_listRepos` | **件数のみ** や粗いバケット | リポ一覧全文、PAT |
| `app_run_start` / `app_run_fail` | 承認済みアプリ ID（内部 UUID）、所要時間帯 | ローカルファイルの絶対パス全文 |
| `flow_step_completed` | フロー ID（`FLOW-NEW` 等）、ステップ番号 | 自由記述の長文（個人が書いた文言） |

**PII は載せない**＝氏名・メール・社員番号・**未承認リポのフルパス**・**トークン**・チャット全文などは **payload に入れない**。必要なら **ハッシュ化した機械キー**や **集計済みカウンタ**に寄せる。

**閲覧**: 運用者は **`/admin/logs`** 等で `telemetry_events` を確認（既存パターン）。**既定 OFF**（`telemetry.url` 未設定）ならクライアントは送らない運用も可。

## VSCode（拡張）

### 製品方針（非エンジニア／野良アプリエンジニア向け）

- **一番目に留まるツール**として、**見た目と動線が最優先**。難解な設定画面の羅列は避ける。
- **迷子にしない**：常に **「いま何の段階か」「次は何か」** が分かる（ステップ番号・短い説明・戻る導線）。
- **フローが核**：例として **「新しくアプリ開発」** と **「既存アプリの改良」** などから入り、選択に応じて **やることリスト（チェックリスト）** を出すと初心者が安心しやすい。
- フロー途中で **作りたいアプリ** を聞き、**Gitea に既に近いリポがあればレコメンド**（キーワード〜 **FastAPI-11** まで段階的に）。
- **仮想環境**は **uv で即時**。元リポがある場合は **そのパッケージ定義**（`pyproject.toml` 等）を起点に同期する動線をフローに組み込む。
- **Gitea への Push** は **ワンコマンド相当の UI**（非エンジニアはターミナルで `git` を打たない）。**ブランチは直感ラベル**（例:「いま作業している版」「みんなに見せる版」）で選ばせ、**選択→確認→ボタン一つ**で完結させる。
- **まだ無いリポジトリの新規作成**も動線に含める（**FLOW-NEW**）。**既存リポへ Push** も **FLOW-IMPROVE** の定番。どちらも「迷わないフロー」の中に置く。
- **Gitea への操作は無理に拡張だけで抱えない**：**組織ポリシー付きのリポ作成**・**サーバ側トークンでの API**・**Push 前の一貫したチェック**などは **FastAPI 側（プロキシ／ゲート API）** に寄せ、拡張は **UI とローカル Git** に集中する（[責務と境界.md](./責務と境界.md) §Gitea 操作の分担）。
- **Push 前に「NoraOps が解析・チェックを回すのに足りるファイル揃い」を検証**する（**FastAPI-14**）。不足があれば **その場で雛形挿入**や、**既定 ON の導入社では FastAPI-12 経由の生成 AI** に「こういうプロンプトで LICENSE を書いて」とフォロー。**不完全なまま Push→放置→解析が死ぬ**ルートをシームレスに潰す。
- **Git はボタン語彙に落とす**（例:**アプリ名＝リポ名**、**作業名＝ブランチ**、**セーブ＝コミット（＋必要なら作業ブランチへ push）**、**リリース＝`main` 向け PR まで**）。**起動ゲートウェイ → オートセーブ → できた！** の三段は [拡張フロー設計.md](./拡張フロー設計.md) の **ステップ①〜③** で定義。

**フローごとの細かい画面・文言・分岐**は [拡張フロー設計.md](./拡張フロー設計.md) に **フロー ID 単位で追記**していく（本表は ID とフェーズの背骨のみ）。

## レビューメモ（この文書で足りるか）

**問題ない点**  
- Phase1 を **AI・GitHub 非依存のコア**に固定し、Phase2 で **実装は揃えるが既定 OFF** の二本立てにすると、ご希望の「導入社に任せる」と整合する。  
- **Git-1** と **FastAPI-12 / 13** の分離で、「移行・AI のコードはあるが使わない」状態を表に残せる。  
- 各 Phase の **完了イメージ**を短く書いたので、リリース判定のたたき台になる。

**注意したい点（実装時にチケットで分解）**  
- **Phase1 の塊は大きい**。スプリントでは **FastAPI-8/9 と Client-1/2** を縦に切るなど、**縦スライス**で中間リリースを挟むと安全。  
- **FastAPI-3** の「どこまで読むか」はコストと Sec-2 に直結するため、Phase1 では **メタ中心＋浅い取得**に割り切る選択肢を検討してよい（表の文言は広めに残している）。

**結論**: 上記原則を追記したうえでの **実装の背骨として採用してよい**ドキュメントに更新した。以降は **ID をチケットにコピペ**し、フェーズ境界で **「AI/GitHub を触らない回帰テスト」** を一回走らせると健全。
