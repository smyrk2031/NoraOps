# NoraOps 機能の役割と責任の境界

[前提と全体像.md](./前提と全体像.md) の **4 本柱**ごとに、**誰が何を決定するか**を固定する。[フェーズ進行.md](./フェーズ進行.md) の「どこまでやったか」の判定にも使う。

## 1. コンポーネント責務マトリクス

| 責務 | ① Gitea | ② FastAPI | ③ VS Code 拡張<br>（Creator + **Runner**） | ④ Tauri（将来） |
|------|---------|------------|---------------------------|-------------------|
| ソース・アプリの正本 | **保持** | 参照・解析・**artifact zip 配布** | read（HTTP artifact + uv） | read |
| Release / アーティファクト | **保持** | メタ・DL URL の仲介も可 | **承認済みのみ**取得対象 | 同左 |
| **公開／承認**（どのリポ×版をユーザーに見せるか） | — | **唯一のゲート**（DB・UI・API） | 指示に従う | 同左 |
| セキュリティ・ライセンス・類似リポの **集約スコア** | — | **計算・保存・API** | 表示のみ | 診断・インライン表示 |
| 禁止コード等の **開発中ポリシー** | — | ルール配布・サーバ側スキャン | **Creator**：エディタ診断 | — |
| uv / Portable Git の導入 | — | manifest **配布** | **PC に配置**（`%LOCALAPPDATA%\NoraOps\runtime`） | 同左 |
| 類似リポ「既に Gitea にあります」 | メタがある | **類似判定 API** を提供 | **Creator**：提案 UI | — |
| トップの DL 案内 | — | **HTML／静的**（.vsix 案内） | 利用 | 利用 |

**Azure OpenAI**（任意）：**② 経由のみ**推奨（キー集中・監査）。③④ はプロンプト直送しない。

## 1b. Gitea 操作の分担（拡張 vs FastAPI）

**方針**: ユーザー動線上は **③ 拡張（Creator）** が窓口でも、**Gitea API を直接・長期トークンで叩き続ける処理**は **② FastAPI に逃がしてよい**（むしろ推奨する場面が多い）。

| 操作の例 | 推奨配置 | 理由 |
|----------|----------|------|
| **新規リポジトリ作成**（組織・可視性・テンプレ README） | **② プロキシ**（`FastAPI-15`） | 組織ポリシー・監査・トークン保管をサーバで一元化 |
| **Push 前の必須ファイル・チェック整合** | **② ゲート API**（`FastAPI-14`） | FastAPI-4〜6 と **同じルール定義**を参照し、解析が空振りしない状態を保証 |
| **実際の `git push`** | **②（サーバー git + GITEA_TOKEN）** | 拡張は zip 転送のみ（v0.5+）。ユーザーに PAT / Credential Helper を出さない |
| **カタログ・承認・類似判定** | **②** | 既存の背骨 |
| **Issue 起票（チェック NG）** | **② → ①** | 既存 |

拡張は **UI・ローカル状態収集・FastAPI 呼び出し**に専念し、**「Gitea に何を作るか」の決定権**は可能な限り **②** に寄せると、**不完全リポが Push されて NoraOps が効かなくなる**事故を減らせる（[フェーズ進行.md](./フェーズ進行.md) `FastAPI-14`／`VSCode-13`）。

## 2. Creator と Runner の住み分け（同一拡張・将来 Tauri）

| 観点 | **Runner**（拡張内 / 将来 Tauri） | **Creator**（拡張） |
|------|-----------------------------------|---------------------|
| 主ユーザー | アプリ**利用者** | **開発者** |
| 必須 | FastAPI、uv、tools | VS Code、Gitea、同左 tools |
| UI | Runner 専用 Webview（カタログ・実行） | ホーム・保存・履歴 |

「同じカタログ API・同じキャッシュキー」に揃え、Tauri 追加時も HTTP 契約を共有する（[ポータルとクライアント.md](./ポータルとクライアント.md)）。

## 3. ① と ② の住み分け

- **①** は保存と認可のみ。解析ロジックは持たない。
- **②** が Gitea API（＋必要なら mirror clone）で取得し、**組織のルール**に照らす。

## 4. データフロー（実行まで）

1. **②** が **承認**し、**公開カタログ**に載ったリポ×版だけを **Runner（拡張 / 将来 Tauri）** に返す。
2. **Runner** が **疎に**必要ファイルのみ取得し、マニフェストに従い **uv** で環境構築・実行（[ポータルとクライアント.md](./ポータルとクライアント.md)）。
3. **②** はテレメトリ等で利用状況だけ受け取る（ソース全文の外部送信は既定 OFF 推奨）。

## 4b. ユーザー識別とリポアクセス（導入社が選べるプロファイル）

**正本の置き方**: **Git 操作の認可（誰がどのリポに push できるか）の正**は **① Gitea** に置くのが自然（オーナー・組織・チーム・コラボレータ）。**②** は **承認済みカタログ**や **プロキシ API** で「運用ポリシー」を重ねるが、**リポ ACL を二重管理しない**のが保守しやすい（作成者＝ Gitea 上のオーナー／管理者に寄せる）。

**「SSO と Gitea のユーザ管理の二択」について**: 実務では **二項対立ではない**ことが多い。**OIDC / OAuth2 / SAML で企業 IdP にログイン**すると、**Gitea 側にもユーザー行ができる**（外部ログイン連携）。**「アカウントの寿命・パスワードポリシー」は IdP**、**「リポへの権限付与の UI・API」は Gitea**、という分担が一般的。

**OAuth について**: **OAuth2 / OIDC は「どうログインするか」のプロトコル**であり、**Azure AD / Keycloak / Okta 等の SSO**は多くの場合 **OIDC（または SAML）で Gitea に接続**する。**「OAuth か SSO か」ではなく、Gitea の認証ソースとして OIDC を選ぶ＝いわゆる SSO**、と理解すると整理しやすい。

**Windows Hello 等**: **デバイス上の生体／PIN（WebAuthn 等）は「その端末で秘密を解錠する手段」**であり、**社員マスタやリポ ACL の正本にはなりにくい**。典型は **IdP ログインの二要素**、または **OS 保管庫に PAT を載せて拡張が解錠して利用**、など **既存 IdP／Gitea トークンと組み合わせる**。

**導入社向けに「準備しておく」プロファイル例**（実装は Gitea の設定＋② の API Key／将来のユーザー紐付けで段階的に）：

| プロファイル | 概要 | 向き先 |
|--------------|------|--------|
| **A. Gitea ローカル** | 組み込みユーザー＋組織／チーム。**最小構成**・PoC。 | 小規模・オフライン気味 |
| **B. OIDC（汎用 SSO）** | Azure AD / Keycloak / Okta 等 → **Gitea OAuth2 ソース**。 | 中〜大規模で標準的 |
| **C. LDAP / Active Directory** | 社内ディレクトリと **Gitea を直接バインド**。 | レガシー IAM が LDAP 中心の場合 |
| **D. ソーシャル／クラウド IdP** | Microsoft / Google 等（**軽いチーム**向け。企業ポリシーは要確認）。 | スタートアップ・外部協業 |
| **E. サービスアカウント分離** | **人間は B/C**、**CI・バッチは専用トークン**（監査しやすい）。 | 運用が育った段階 |

**NoraOps ② が「独自ユーザ DB」を持つ案**は、**Gitea 権限と二重化**しやすいので **初期は避け**、どうしても必要なら **IdP の subject と Gitea ユーザー名のマッピング表だけ**など **最小の橋**に留めるのが安全、とする（詳細は実装 RFC）。

## 5. 明示的に「やらない」こと（初期）

- **自動マージ**（PR 草案は人間がマージ）。
- **クライアントに本番秘密を埋め込む**。
- **LLM なしで核が止まる**設計にしない。
