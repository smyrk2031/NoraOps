# 主要機能の検討と実現性（NoraOps）

[構想資料.md](./構想資料.md) の思想に加え、**[前提と全体像.md](./前提と全体像.md) の 4 本柱**を前提にする。本資料は **実装の現実性・依存関係・コスト**の整理。**フェーズの一覧だけ**知りたい場合は [フェーズ進行.md](./フェーズ進行.md) を先に読む。

## 1. プラットフォーム前提（合意したいこと）

| 前提 | 内容 |
|------|------|
| 名称 | **NoraOps** |
| ① アプリの置き場 | **Gitea**（当面）。将来 **GitHub 等**へ差し替え可能な抽象層 |
| ② バックエンド | **FastAPI**：解析、**運用側の承認で「公開カタログ」に載せる**、ダッシュボード、トップで **クライアント＆拡張のダウンロード** |
| ③ VS Code 拡張 | **Creator**（開発・保存・Gitea）+ **Runner**（承認済み検索・uv 実行）。配布の正は **.vsix** |
| ④ Tauri（将来） | **Runner のみ** — VS Code を避けたい利用者向け。API は ② と同じ |
| 実行経路 | Gitea Release 等を参照し **uv** で実行。上級者はそのまま VS Code で開発 |
| 生成 AI（その先） | **Azure OpenAI**（キー・環境名・デプロイ）。**機能単位で ON/OFF** |

## 2. 機能マップ（構想資料 7章・8章 → 実装単位）

下表は **実現難易度** と **主な依存** の目安。詳細仕様は個別に起票する。

| ID | 機能（構想での呼び名） | 難易度 | 主な依存 | 備考 |
|----|------------------------|--------|----------|------|
| F0 | ツールチェーン自動導入（uv / Git） | 低 | manifest + 配布 API | ④拡張に既存 → ③と **クライアント提供 B（MC1）** で共有可（[配布検討.md](./配布検討.md)） |
| F1 | アプリカタログ・ワンクリック・`uv run` | 低〜中 | Gitea API + manifest | **承認済みカタログ（MA1）**後は **公開 API のみ**が③④。**疎同期**は別難易度 |
| FA | **公開承認ワークフロー** | 中 | DB・管理 UI・監査・`published` API | 「Gitea 全件表示」との切り分け |
| F2 | リポジトリ横断メトリクス（星・更新・Release 等） | 低 | Git API + 集計 | サーバの Analyzer 周辺 |
| F3 | ポリシー・命名・ブランチ等のルール検査 | 低〜中 | リポメタデータのみで可 | 既存 `policy_violations` 拡張で可 |
| F4 | ライセンス検出・依存 SBOM | 中 | クローン or  tarball / package マニフェスト取得 | ストレージ・バッチ・法務ポリシー要検討 |
| F5 | セキュリティ（秘密情報スキャン・依存脆弱性） | 中〜高 | スキャナ統合・DB・更新頻度 | **Trivy / Gitleaks 等**の選定と運用 |
| F6 | コード検索・ベクトル検索・インデックス | 中〜高 | 埋め込みストア・チャンク設計 | Azure OpenAI Embeddings + ベクトル DB |
| F7 | アプリ全体への自然言語質問（RAG） | 中〜高 | F6 + LLM + 監査ログ | トークンコスト大・**必ず feature flag** |
| F8 | 危険箇所の **PR 草案生成**（自動マージしない） | 中 | Git Host API + LLM | GitHub/Gitea の PR API 差異を吸収 |
| F9 | Issue / PR 上の **AI 下書き・要約** | 中 | Webhook + LLM | レート制限・スコープ最小化 |
| F10 | **匿名アイデア相談**（構想 8章） | 中〜高 | 匿名化設計・保存方針・モデレーション | 個人情報・禁止事項・ログ監査が必須 |
| F11 | 属人化指数・理解難易度・OSS 寿命等 | 中〜高 | 活動データ・外部メトリクス | 段階的に指標を増やす |
| F12 | 過去障害類似検知 | 高 | インシデント DB との連携が現実的 | 手元 Markdown からでもプロトタイプ可 |

**難易度**: 低 = 既存パターンで短期、高 = 設計・運用・コンプライアンスが重い。

## 3. フェーズ提案（無駄を減らす積み方）

### Phase A（今ある土台を NoraOps として言語化・改名のみに近い）

- F0, F1, F2, F3 を **製品ストーリーに載せる**（ドキュメント・表示名の NoraOps 化）。
- ② **トップページ**で ③用取得手順・④ `.vsix` への導線を明確化（[フェーズ進行.md](./フェーズ進行.md) M1）。
- **Gitea のみ** を前提にしつつ、**Git Provider** を文書化（コードは薄くてよい）。
- 直後に **FA（承認＋`published` カタログ）** を載せると、③④ の仕様が一本化しやすい（[フェーズ進行.md](./フェーズ進行.md) **MA1**）。

### Phase B（「守られている感」を出す解析）

- F4 の一部（LICENSE ファイル・主要 manifest の静的解析）。
- F5 の軽量版（パターンによる秘密らしき文字列、既知CVEとの照会はオプション）。
- ダッシュボードで **重大度と説明文** を構想の「良い例」トーンに寄せる（威圧ではなく提案）。

### Phase C（組織摩擦削減＝AI 本格）

- Azure OpenAI 接続基盤（**環境名・キー・デプロイ名**・**日次/ユーザー上限**）。
- F6 の最小版（単一リポ・README + 主要ファイルのチャンク + 検索）。
- F7 はベータ扱い・**デフォルト OFF**。

### Phase D（Git ホスト連携とワークフロー）

- GitHub 適配層、Webhook、F8/F9。
- F10 は **別チャネル（専用 UI or 拡張コマンド）** とデータ最小化設計が先。

## 4. コスト・機能フラグ（合意事項のたたき台）

| 種別 | 例 | 制御の仕方 |
|------|-----|------------|
| LLM 呼び出し | チャット・PR 草案・要約 | `NORAOPS_FEATURE_*` + ユーザー/日あたり上限 |
| Embedding | コードインデックス | バッチ間隔・対象ブランチを絞る |
| 外部スキャナ | Trivy | CI での実行 vs サーババッチ |

**方針**: 課金や運用が変わっても **核（①Gitea・②の一覧/簡易解析・③④の uv 実行パス）** が生きるようにする。

## 5. Gitea と GitHub の位置づけ

- **同一責務**: 「アプリとバージョンの権威（Source of truth）」「Issue/PR の載せ場」。
- **差分**: API と権限モデルが異なるため **アダプタ**（[責務と境界.md](./責務と境界.md)）で吸収する。
- **短期**: Gitea 実装 + GitHub を **Null または read-only スタブ**でも、境界のテストが書ける。
